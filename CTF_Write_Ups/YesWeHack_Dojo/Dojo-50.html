Challenge description

## Description

Bucket Vault implements a secure file storage system using pre-signed URLs with signatures. Generate time-limited access tokens for files stored in the vault, with built-in signature verification to ensure only authorized requests can retrieve protected content.

Report

Bug type: [Path Traversal (CWE-22)](https://cwe.mitre.org/data/definitions/22.html)

Scope: https://dojo-yeswehack.com/challenge-of-the-month/dojo-50

Host: -

Endpoint: ?action=download

Vulnerable part: GET parameter

Part name: filename

Payload: filename=public/./super_secret.txt

Technical env.: PHP

App. fingerprint: -

CVE: -

Impact: Arbitrary File Read

CVSS: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N

Solution

The application implements a custom pre-signed URL mechanism to restrict access to files stored in a vault. However, inconsistent validation between the sign and download functionalities makes it possible to manipulate the filename after signature generation and access unauthorized files through a Path Traversal vulnerability.

PoC

Vulnerability 1: Inconsistent Validation

The application applies different validation rules depending on the action:

  • Signing

elseif ($action === 'sign')

  • Download

if ($action === 'download')

Vulnerability 2: Signature depends on user-controlled input

  • The signature is computed using the raw filename
  • No normalization

Vulnerability 3: Path Traversal in File Access

This allows:

Vulnerability 4: Sanitization Mismatch

  • sanitizeFilename() is only used during signing
  • Not used during verification or file acces

Which leads to trust boundary violation

Exploitation

Step 1

The first step is to understand how the vault works. When a first request is submitted without any input the result explains:

  1. ACTION=SIGN

    Generate a presigned URL with an HMAC signature. The URL is valid for 3600 seconds.
Example ?action=sign&filename=document.txt

  2. ACTION=DOWNLOAD

    Retrieve a file using a valid presigned signature before it expires.
Example ?action=download&filename=file&expires=ts&signature=hash

This gives us already a first look at what we are trying to accomplish. There are 3 public documents inside public directory and we want to escape restrictions to be able to see super_secret.txt.

Risk

This vulnerability allows:

  • Arbitrary file read within the application directory
  • Access control bypass (restricted files become accessible)
  • Potential exposure of:
    • Sensitive files
    • Configuration files
    • Secrets or credentials

If extended in a real-world scenario, this could lead to:

  • Full system compromise (via config leaks)
  • Lateral movement

Remediation

1. Enforce Consistent Validation

2. Normalize File Paths

3. Avoid Custom Signature Mechanisms

Use AWS SDK:

4. Canonicalize Input Before Signing

  • Resolve path before signing

The challenge features an AWS-style presigned URL service where users can sign files from the public/ bucket to get a time-limited HMAC signature, then download them using that signature. A private file super_secret.txt sits outside the public prefix and holds the flag.

The vulnerability lies in an asymmetric treatment of the filename: str_contains($filename, '..') blocks path traversal - but sanitizeFilename(), which strips all ASCII control characters including \n, only runs after the check inside generatePresignedUrl(). By injecting a literal newline between the two dots, the contiguous .. is broken and bypasses the check. The sanitization then removes the \n before computing the HMAC, producing a valid ../ traversal in the signed path.

Official payload

Using this payload, str_contains sees . + \n + . - no contiguous .. - the check passes. sanitizeFilename() strips the \n and the HMAC is computed over public/../super_secret.txt. At download, verifySignature() recomputes the HMAC over the same clean path and it matches. getFileContents() then resolves files/public/../super_secret.txt to files/super_secret.txt and returns the flag.
